## 一、Critical（必须改，会造成数据丢失或资金/库存错账）

### C1 · 商品每被编辑一次，就删光所有用户的购物车条目，并让历史订单失去库存回滚能力

**位置**：`backend/app/services/product_service.py:213-228`（`_replace_skus`），被 `update_product`（:265）无条件调用

```python
def _replace_skus(db, product, skus):
    # MVP 采用整体替换：删除旧 SKU 后重建
    db.query(Sku).filter(Sku.product_id == product.id).delete(synchronize_session=False)
    db.flush()
    for item in skus:
        db.add(Sku(...))
```

**为什么错**：`Sku` 是两张表的外键父表，两条外键规则在这里同时引爆：

| 引用方 | 外键规则 | 删除 SKU 后的结果 |
|---|---|---|
| `cart_items.sku_id` | `ON DELETE CASCADE`（`models/cart_item.py:19`） | **购物车条目被物理删除** |
| `order_items.sku_id` | `ON DELETE SET NULL`（`models/order_item.py:28`） | 历史订单 `sku_id` 变 NULL |

而 `update_product` 会**无条件**走整体替换——哪怕只改商品名或描述，SKU 也会被删光重建。

**实测证据**（真实模型 + 真实外键，临时库）：

```
改前 购物车条目数 = 1        改后 购物车条目数 = 0
改前 订单明细 sku_id = 1     改后 订单明细 sku_id = None
```

**三重后果**：

1. **用户购物车被清空**。任何一次商品编辑，所有把该商品放进购物车的用户，条目凭空消失。这是静默的数据丢失，用户只会觉得"我明明加过"。
2. **库存回滚永久失效**。`order_service._rollback_stock:318` 的判断是 `if item.sku_id:`，`sku_id` 为 NULL 后直接跳过，只打一条 warning。于是「下单扣库存 → 商品被编辑 → 用户取消订单」这条链**库存永远不回来**。每编辑一次，泄漏一批。
3. **删除守卫失灵**。`product_service.delete_product:273-278` 通过 `OrderItem JOIN Sku ON sku_id` 判断有无历史订单，`sku_id` 为 NULL 后 join 不到 → 守卫放行 → 有历史订单的商品也能被物理删除。（`merchant_service.delete_product:124` 用 `OrderItem.product_id`，是对的——同一个项目里两套判断，说明这里确实被漏掉了。）

**怎么改**：把"整体替换"改成"差量同步"，按 `attrs_key` 对齐 upsert，只删真正消失的 SKU；并对「已被订单引用」的 SKU 改为软删除（`is_active=False`）而非物理删除。

```python
# 替换 product_service.py:213-228
def _sync_skus(db: Session, product: Product, skus: list[SkuIn]) -> None:
    existing = {s.attrs_key: s for s in
                db.scalars(select(Sku).where(Sku.product_id == product.id)).all()}
    incoming_keys = set()
    for item in skus:
        key = build_attrs_key(item.attrs)
        incoming_keys.add(key)
        if cur := existing.get(key):
            cur.sku_code = item.sku_code
            cur.price = item.price
            cur.stock = item.stock
            cur.is_active = item.is_active
        else:
            db.add(Sku(product_id=product.id, sku_code=item.sku_code, attrs=item.attrs,
                       attrs_key=key, price=item.price, stock=item.stock,
                       is_active=item.is_active))
    for key, cur in existing.items():
        if key not in incoming_keys:
            # 有订单引用则软删除，保住 sku_id，库存回滚与历史订单都还能对上
            if db.scalar(select(OrderItem.id).where(OrderItem.sku_id == cur.id).limit(1)):
                cur.is_active = False
            else:
                db.delete(cur)
```

配套：`update_product` 补上 `_check_sku_code_conflict`（见 M4），并给 `cart_items.sku_id` 的外键从 `CASCADE` 改成 `SET NULL` + 应用层清理，或干脆不动外键但禁止物理删除 SKU。

### C2 · 前端每次点击都生成新的幂等键，幂等机制形同虚设

**位置**：`frontend/src/views/Checkout.vue:257-279`

```javascript
async function submitOrder() {
  if (!canSubmit.value) return
  submitting.value = true
  try {
    const idemKey = crypto.randomUUID()      // ← 每次调用都换一个
    const order = await createOrder({...}, idemKey)
```

**为什么错**：幂等键的语义是「**同一次逻辑提交**的重试要携带**同一个** key」。放在点击处理函数里每次新建，等于每次重试都被后端视为全新请求：

- 网络超时 / 用户刷新后重试 / 移动网抖动 → 后端 `idempotency_keys` 表里查不到重复 → **创建第二笔订单、扣第二次库存**。
- 后端 `order_service.create_order` 花了大力气用 `ON CONFLICT DO NOTHING` 做原子占位（这部分实现是对的），结果被前端这一行抵消了。

`submitting` 只挡住"同一请求未返回前的连点"，挡不住"请求失败后用户再点一次"。

**怎么改**：进结算页时生成一次并持有，提交成功后再轮换。

```javascript
// 顶层
let idemKey = crypto.randomUUID()

async function submitOrder() {
  if (!canSubmit.value || submitting.value) return
  submitting.value = true
  try {
    const order = await createOrder({...}, idemKey)
    idemKey = crypto.randomUUID()   // 成功后才换，失败重试沿用旧 key
    ...
```

顺带：`crypto.randomUUID()` **只在安全上下文可用**（HTTPS / localhost）。用 `http://192.168.x.x` 部署时它是 `undefined`，直接 `TypeError`，**订单根本提交不出去**。加个降级（见 M7）。

## 二、Major（建议本迭代修）

### M1 · 停用账号的 token 在有效期内仍畅通，改密码也不踢掉旧会话

**位置**：`backend/app/api/deps.py:35-39`、`services/auth_service.py:85-92`

`deps.py` 注释已自认这是「S-12 已知限制」：`get_current_user` 不校验 `is_active`。而 `jwt_access_token_expire_minutes = 1440`，也就是**封禁一个用户后，他还能正常下单 24 小时**。

更麻烦的是 `change_password` 只改哈希，没有 token 版本号 → **账号被盗后用户改密码，攻击者的 token 依然有效 24 小时**。这是电商场景里真正会被拿来打的问题。

**改法**（低成本）：`users` 表加 `token_version: int = 0`，签发时写进 payload，`get_current_user` 比对；改密码 / 封禁时 `token_version += 1`。同理可顺手补上 `is_active` 校验：

```python
user = db.get(User, int(subject))
if user is None or not user.is_active:
    raise BizException(ErrorCode.TOKEN_INVALID, "账号不存在或已停用")
if payload.get("token_version", 0) != user.token_version:
    raise BizException(ErrorCode.TOKEN_INVALID, "登录凭证已失效，请重新登录")
```

### M2 · 登录失败计数表无上限、永不回收，可被打成内存泄漏

**位置**：`backend/app/services/auth_service.py:19-46`

`_FAILURES: dict[str, list[float]]` 以「账号字符串」为键。成功登录才会 `_clear_failures`，锁定期满只清 `_LOCKED_UNTIL`，**`_FAILURES` 里那条记录永久留存**。

攻击者用随机账号名刷 `/auth/login`（永远不成功、也就永远不清），每请求往字典里塞一个键 → **进程内存单调增长至 OOM**。这是比撞库更廉价的一种打法。

**改法**：① `_FAILURES` 加容量上限 + LRU 淘汰；② 定时清理过期窗口；③ 长痛不如短痛，直接迁 Redis（`INCR` + `EXPIRE`，天然带 TTL）。

### M3 · 上传接口先把整个文件读进内存，再校验 5MB 上限

**位置**：`backend/app/api/v1/admin/upload.py:37-39`

```python
content = await file.read()          # ← 先全量读入内存
if len(content) > MAX_SIZE:
    raise BizException(...)          # ← 才判断大小
```

`UploadFile` 超过 1MB 会落盘，但 `await file.read()` 仍会把整个文件一次性读进内存。传 2GB 文件 → **2GB 内存尖峰**，几个并发就能打挂进程。管理员权限虽然收窄了攻击面，但商家后台一旦复用这个接口就变成外部可打。

**改法**：分块读，超限立即中止并断开；同时在校验 `Content-Length` 头做前置拒绝。

```python
MAX_SIZE = 5 * 1024 * 1024
buf = bytearray()
while chunk := await file.read(64 * 1024):
    buf.extend(chunk)
    if len(buf) > MAX_SIZE:
        raise BizException(ErrorCode.PARAM_INVALID, "图片大小不能超过 5MB")
content = bytes(buf)
```

### M4 · `update_product` 漏了 `sku_code` 唯一性预检，只落到笼统的 409

**位置**：`product_service.py:254-268`

`create_product:233` 调了 `_check_sku_code_conflict`，`update_product` **没调**。编辑商品时把某个 SKU 编码改成别的商品已用的值 → 唯一约束报错 → 被 `exceptions.py:54` 的 `IntegrityError` 兜底成 `409 资源冲突，请重试`。

不算崩，但用户看到的是"资源冲突，请重试"而不是"SKU 编码已存在：XXX"，重试一百次也不会成功。**报错信息把可修复问题伪装成了瞬时故障**。

**改法**：`update_product` 里在 `_sync_skus` 前补 `_check_sku_code_conflict(db, [s.sku_code for s in payload.skus])`。

### M5 · JWT 存在 localStorage + `JSON.parse` 裸调，一个 XSS 全盘皆输、一次存储损坏直接白屏

**位置**：`frontend/src/store/user.js:6-7`

```javascript
user: JSON.parse(localStorage.getItem('user') || 'null')
```

两个问题：

1. **安全**：token 在 `localStorage`，任何 XSS 都能 `localStorage.getItem('token')` 拿走，且服务端无 token 版本机制（M1）→ 有效期 24 小时内无法吊销。当前 `v-html` 三处渲染的都是**封闭集合里的静态 SVG**（见「已证伪」），没有活的注入点，所以暂不可利用——但这是"目前碰巧安全"，不是"设计上安全"。
2. **健壮性**：`JSON.parse` 没有 try/catch。localStorage 里 `user` 一旦被写坏（旧版本格式、手动改、存储截断），**store 初始化就抛 SyntaxError**，`useUserStore()` 在路由守卫里调用 → 整个应用白屏，且无法自愈，用户只能手动清缓存。

对比：`store/cart.js:16-22` 的 `readGuest()` **有** try/catch。同一份代码两种标准，说明这里是被漏掉的。

**改法**：短期至少包一层；中期迁到 `httpOnly + Secure + SameSite` Cookie，让 JS 读不到 token。

```javascript
function readUser() {
  try {
    const raw = JSON.parse(localStorage.getItem('user') || 'null')
    return raw && typeof raw === 'object' ? raw : null
  } catch {
    localStorage.removeItem('user')
    return null
  }
}
```

### M6 · 购物车「全不选」状态存不住，一刷新就变全选

**位置**：`frontend/src/store/cart.js:204-208`

```javascript
syncChecked() {
  const validKeys = new Set(this.validItems.map((i) => i.key))
  const kept = this.checked.filter((k) => validKeys.has(k))
  this.checked = kept.length ? kept : Array.from(validKeys)   // ← 空数组被当成"没初始化"
}
```

用户把勾选全部取消（`checked = []`），此时 `kept` 为空 → 走 `else` 分支 → **自动全选回去**。任何触发 `load()` 的动作（切页、加购、刷新）都会把用户的"全不选"状态重置。`checked` 空数组到底是"用户主动全不选"还是"首次进入未初始化"，这里没有区分。

**改法**：用 `loaded` 标志区分首次初始化与后续同步。

```javascript
syncChecked() {
  const validKeys = new Set(this.validItems.map((i) => i.key))
  if (!this.loaded) {
    this.checked = Array.from(validKeys)          // 首次进页面才默认全选
    return
  }
  this.checked = this.checked.filter((k) => validKeys.has(k))
}
```

### M7 · `crypto.randomUUID()` 在 HTTP 部署下不存在，下单直接挂

**位置**：`Checkout.vue:261`

`crypto.randomUUID` 属于 Secure Context API，只在 HTTPS 或 localhost 可用。内网 IP / 测试机用 HTTP 打开时它是 `undefined` → `TypeError: crypto.randomUUID is not a function` → 被 `catch (e) {}` 静默吞掉，**用户点提交毫无反应**（连报错提示都不会有，因为异常在本地就抛了，走不到 axios 拦截器）。

**改法**：

```javascript
function newIdemKey() {
  if (globalThis.crypto?.randomUUID) return crypto.randomUUID()
  return `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 10)}`
}
```

同时 `catch (e)` 不该是空的——本地异常也要给用户反馈。

## 四、已证伪（我本来怀疑有问题，实测/读码后确认没问题）

**这一节同样是结论，不要跳过。** 它划定了"不用再怀疑"的边界。

| 怀疑点 | 结论 | 依据 |
|---|---|---|
| `pg_insert` 在 SQLite 上会编译失败或静默丢 `ON CONFLICT` | **能跑**。生成 `INSERT ... ON CONFLICT (user_id,"key") DO NOTHING RETURNING id`，二次插入返回 `None` | 实跑 SQLite 3.49.1 双次插入 |
| SQLite 绑定参数上限只有 999，`cart_item_ids` 批量下单会挂 | **不成立**。本机 3.49.1 上限 32766 | 实测 |
| 三处 `v-html` 是 XSS 入口 | **不是**。`artFor()` 只从静态 `ART` 字典返回，`LineIcon` 无动态 `:path` 绑定，都是封闭集合 | 读 `product-art.js` + grep 全部调用点 |
| 商家可越权操作他店商品 | **防护到位**。`merchant_service._get_owned_product` 强制 `product.merchant_id == merchant.id`，且统一返回 404 不暴露存在性 | 读码 |
| 管理端有接口漏鉴权 | **没有**。`get_current_admin` / `get_current_super_admin` 全量覆盖，`deps.py` 四层齐全 | grep 全部 `APIRouter` 声明 |
| 有硬编码密钥 / 危险日志 / 命令注入 | **机械扫描 P0=0、P1=0**。日志全部参数化（`%s`），无 f-string 拼接；无 `eval` / `pickle` / `os.system` / `subprocess` | `code-review-report` 全量 diff 扫描 |

另外：上一轮报告的 `JWT_SECRET_KEY` 默认值问题**已经修了**，`main.py:18` 在生产环境会拒绝启动；订单幂等竞态也从"先查后插"改成了原子占位。这两条已经闭环。

## 五、建议修复顺序

| 批次 | 内容 | 理由 |
|---|---|---|
| **第 1 批（本周）** | C1 SKU 差量更新、C2 幂等键复用、M4 sku_code 预检 | 三处都在「商品编辑 → 下单」主链路上，是**真实用户可感知的数据丢失与重复下单**。C1 改动集中在 `product_service` 一个函数，可独立上线 |

| **第 3 批** | M5 localStorage 容错、M6 勾选状态、M7 幂等键降级、m8 / m10 / m12 | 前端健壮性，一次性打包 |
| **第 4 批** | m1~m13 其余 + 大组件拆分 | 技术债清理，跟功能迭代一起走 |
